# 4차 회의록 - 2026-05-29

## 1. 회의 목적

이번 회의에서는 3차 회의에서 정리한 화면 구조와 데이터 구조를 바탕으로 AI를 활용해 구현한 결과를 검토하였다. 단순히 앱이 동작하는지 확인하는 것에서 그치지 않고, 요구사항 분석과 설계 문서에 비추어 구현 결과가 적절한지 확인하고 개선사항을 도출하는 것을 목표로 하였다.

또한 과제 주제인 **프로세스에 입각한 바이브코딩의 효과**를 분석하기 위해, 일반적인 짧은 프롬프트와 요구사항/설계를 반영한 프로세스 기반 프롬프트의 차이를 비교하였다.

---

## 2. 이전 회의 내용 확인

3차 회의에서는 다음 사항을 정리하였다.

- 기록 목록 화면, 기록 추가/수정 화면, 상세 보기 화면, 추천 화면 설계
- 영화와 책을 공통 데이터 구조로 관리하기로 결정
- `title`, `type`, `genre`, `rating`, `status`, `review`, `recommended`, `recommendReason` 등의 데이터 필드 정의
- 별점 4점 이상 항목을 추천 목록으로 표시하는 기준 설정

이번 회의에서는 위 설계가 실제 구현 결과에 얼마나 반영되었는지 검토하였다.

---

## 3. 논의 안건

### 3.1 AI 활용 구현 결과 검토

AI를 활용하여 MOBIE의 기본 웹앱 구현을 진행하였다. 구현 결과는 정적 웹앱 형태로 구성되었으며, 별도 서버나 데이터베이스 없이 브라우저에서 실행할 수 있도록 하였다.

검토한 구현 기능은 다음과 같다.

- 영화/책 기록 추가
- 기록 목록 조회
- 상세 보기
- 기록 수정
- 기록 삭제
- 영화/책 유형 필터링
- 최신순, 별점순, 제목순 정렬
- 별점 4점 이상 추천 목록
- 장르별 추천 필터
- 입력값 누락 시 오류 메시지 표시
- 브라우저 `localStorage`를 활용한 데이터 저장

### 3.2 요구사항 대비 구현 결과 확인

2차 회의에서 정리한 기능 요구사항과 비교했을 때, 핵심 기능인 CRUD, 필터링, 정렬, 추천 기능은 대부분 구현된 것으로 확인하였다.

다만 구현 결과를 검토하면서 다음과 같은 개선 필요 사항을 발견하였다.

- 추천 기준이 화면에서 더 명확히 드러나야 한다.
- 사용자가 추천 여부를 체크했을 때 추천 이유 입력을 유도해야 한다.
- 상세 보기 화면에서 추천 이유를 더 잘 확인할 수 있어야 한다.
- 목록 화면에서 영화와 책의 구분이 시각적으로 더 명확해야 한다.
- 테스트 결과를 별도 문서로 남겨야 한다.
- 이미지도 같이 사용할 수 있으면 좋겠다.

### 3.3 일반 프롬프트와 프로세스 기반 프롬프트 비교

이번 회의에서는 바이브코딩 과정에서 프롬프트의 구체성과, 프로세스 기반의 작업이 구현 결과에 미치는 영향을 논의하였다.

#### 일반 프롬프트 예시

```text
영화/책 추천 기록 앱 만들어줘.
```

일반 프롬프트의 예상 문제점은 다음과 같다.

- 기능 범위가 모호하다.
- 어떤 화면이 필요한지 명확하지 않다.
- 데이터 항목이 누락될 수 있다.
- 추천 기능의 기준이 불명확하다.
- 테스트 기준을 세우기 어렵다.
- AI가 임의로 기능을 추가하거나 과하게 복잡한 구조를 제안할 수 있다.

#### 프로세스 기반 프롬프트 예시

```text
다음 요구사항과 설계 문서, 회의록을 기반으로 영화/책 추천 기록 웹앱을 구현해줘.

기능 요구사항:
- 영화/책 기록 추가
- 제목, 유형, 장르, 별점, 감상 상태, 한 줄 감상평, 추천 여부 입력
- 목록 조회
- 영화/책 필터링
- 별점순 정렬
- 상세 보기
- 수정/삭제
- 별점 4점 이상 추천 목록
- 장르별 추천 필터

비기능 요구사항:
- 입력값 누락 시 오류 메시지 표시
- 목록은 카드 형태로 한눈에 구분
- 추천 기준은 화면에 명확히 표시
- 코드 구조는 유지보수 가능하게 분리

데이터 구조:
id, title, type, genre, rating, status, review, recommended, recommendReason

화면:
- 기록 목록 화면
- 기록 추가/수정 화면
- 상세 보기 화면
- 추천 화면
```

프로세스 기반 프롬프트의 장점은 다음과 같다.

- 요구사항 누락이 줄어든다.
- 화면 구조와 데이터 구조가 일관되게 구현된다.
- 구현 결과를 검토할 기준이 명확해진다.
- 테스트 항목을 만들기 쉽다.
- 수정해야 할 범위와 우선순위를 판단하기 쉽다.

## 4. 구현 결과 검토

### 4.1 잘 반영된 부분

- 요구사항 문서의 핵심 기능이 실제 기능으로 연결되었다.
- 설계 문서에서 정의한 주요 화면 흐름이 구현 결과에 반영되었다.
- 영화와 책을 같은 데이터 구조로 관리하여 필터링과 정렬이 단순해졌다.
- 별점 4점 이상이라는 추천 기준을 기능으로 구현할 수 있었다.
- 입력값 검증을 통해 비기능 요구사항 중 사용성 요구를 일부 반영하였다.

### 4.2 부족하거나 개선이 필요한 부분

- 추천 기준과 추천 여부의 차이를 사용자에게 더 명확히 설명할 필요가 있다.
- 실제 테스트 결과를 아직 문서화하지 않았으므로 테스트 보고서 작성이 필요하다.
- UI가 기본 기능 중심으로 구성되어 있어 시각적 완성도를 더 높일 수 있다.
- 수정/삭제 기능이 의도대로 작동하는지 다양한 예시 데이터로 검증해야 한다.
- `localStorage` 저장 방식은 간단하지만, 여러 사용자 환경이나 서버 저장에는 한계가 있다.

## 5. 주요 결정 사항

- 4차 회의에서는 구현 결과를 최종 완료로 보지 않고, 개선사항을 도출하는 단계로 정리한다.
- 5차 회의에서는 4차 회의에서 발견한 개선사항을 실제로 반영한다.
- 일반 프롬프트와 프로세스 기반 프롬프트 비교 내용을 최종 보고서의 분석 내용으로 활용한다.
- AI가 만든 결과를 그대로 제출하지 않고, 요구사항 문서와 설계 문서를 기준으로 사람이 검토하고 수정하는 과정을 거친다

## 6. 개선사항 목록

4차 회의에서는 구현 결과를 검토한 뒤, 개선사항을 팀원별 의견으로 나누어 정리하였다. 각 개선사항은 5차 회의에서 수정 및 테스트 대상으로 삼는다.

### 6.1 영주

- [ ] 추천 여부를 체크했을 때만 추천 이유 입력란이 나타나도록 개선한다.
- [ ] 추천 여부를 체크하지 않은 경우에는 추천 이유 입력란을 숨기거나 비활성화한다.
- [ ] 사용자가 추천 여부를 선택했을 때 추천 이유를 자연스럽게 입력할 수 있도록 UI 흐름을 개선한다.

### 6.2 수민

- [ ] 추천 기준을 화면에서 더 명확히 설명한다.
- [ ] 추천 여부와 별점 기반 추천 목록의 차이를 문서와 화면에서 구분한다.
- [ ] 장르 선택 시 해당 장르의 추천 항목만 표시되는지 확인한다.

### 6.3 승윤

- [ ] AI 활용 프롬프트와 결과를 `docs/ai-prompts.md`에 정리한다.
