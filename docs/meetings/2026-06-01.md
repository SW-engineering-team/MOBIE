# 5차 회의록 - 2026-06-01

## 1. 회의 목적

이번 회의에서는 4차 회의에서 도출한 개선사항을 바탕으로 구현 결과를 수정하고, 수정된 기능이 요구사항에 맞게 동작하는지 테스트하였다.  
특히 추천 여부 입력 방식, 추천 기준 표시, 필터/정렬/추천 기능 검증, AI 프롬프트 비교 자료 정리를 중심으로 논의하였다.

5차 회의의 목표는 단순히 기능을 추가하는 것이 아니라, **AI가 생성한 구현 결과를 사람이 검토하고 수정하여 품질을 높이는 과정**을 증빙하는 것이다.

---

## 2. 이전 회의 내용 확인

4차 회의에서는 AI를 활용한 구현 결과를 검토하고 다음 개선사항을 도출하였다.

- 영주: 추천 여부를 체크했을 때만 추천 이유 입력란이 나타나도록 개선
- 수민: 추천 기준과 추천 여부의 차이를 화면과 문서에서 명확히 구분
- 승윤: AI 활용 프롬프트와 결과를 정리하고 테스트 결과를 문서화

이번 회의에서는 위 개선사항을 실제 수정 및 테스트 대상으로 삼았다.

---

## 3. 개선사항 반영 결과

### 3.1 영주 의견 반영

영주는 기록 추가 화면에서 **추천 여부를 체크하지 않아도 추천 이유 입력란이 항상 보이는 점**이 어색하다고 의견을 제시하였다.  
이에 따라 추천 여부 체크박스를 기준으로 추천 이유 입력란의 표시 방식을 개선하기로 하였다.

반영 방향은 다음과 같다.

- 추천 여부를 체크하면 추천 이유 입력란을 보여준다.
- 추천 여부를 체크하지 않으면 추천 이유 입력란을 숨기거나 비활성화한다.
- 추천 여부가 선택된 상태에서는 추천 이유 입력을 유도한다.
- 추천 여부가 선택되지 않은 경우 추천 이유가 없어도 저장할 수 있도록 한다.

이 개선은 사용자가 불필요한 입력란을 보지 않도록 하여 입력 흐름을 단순하게 만드는 효과가 있다.

### 3.2 수민 의견 반영

수민은 추천 기능에서 **추천 여부**와 **별점 기반 추천 목록**의 의미가 혼동될 수 있다고 보았다.  
따라서 화면과 문서에서 두 개념을 구분하기로 하였다.

정리한 기준은 다음과 같다.

- `recommended`: 사용자가 직접 추천 여부를 표시한 값
- 추천 목록: 별점이 4점 이상인 항목을 기준으로 자동 표시되는 목록
- 장르 추천: 선택한 장르 중 별점 4점 이상인 항목만 표시

이 기준을 통해 추천 기능의 동작 방식이 더 명확해졌고, 테스트 기준도 구체화되었다.

### 3.3 승윤 의견 반영

승윤은 AI 활용 과정과 테스트 결과를 별도 문서로 남겨야 한다고 정리하였다.  
이에 따라 일반 프롬프트와 프로세스 기반 프롬프트의 비교 기준을 정리하고, 테스트 결과를 문서화하기로 하였다.

정리할 문서는 다음과 같다.

- `docs/test-report.md`: CRUD, 필터/정렬, 추천 기능 테스트 결과
- `docs/final-report-draft.md`: 최종 결과 보고서 초안

### 3.4 Direct prompting 결과물과 프로세스 기반 결과물 비교

이번 회의에서는 단순 프롬프트로 생성한 결과물과 요구사항/설계/회의록을 반영한 프로세스 기반 결과물을 비교하였다.

비교 대상은 다음과 같다.

- Direct prompting 결과물: `output/direct-prompting/prompt_only_archive_v2.html`
- 프로세스 기반 결과물: `output/process-based-prompting/index.html`, `styles.css`, `app.js`

| 비교 항목     | Direct prompting 결과물                                 | 프로세스 기반 결과물                                                                                      | 더 나은 점                                        |
| ------------- | ------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- | ------------------------------------------------- |
| 요구사항 반영 | 제목, 유형, 평점, 메모 중심의 간단한 기록 기능 구현     | 요구사항 문서의 제목, 유형, 장르, 별점, 상태, 감상평, 추천 여부, 추천 이유 반영                           | 요구사항 누락이 적고 과제에서 설명하기 쉽다.      |
| CRUD          | 추가와 삭제 중심                                        | 추가, 조회, 상세 보기, 수정, 삭제 구현                                                                    | CRUD 구조가 완성되어 기능 검증 범위가 명확하다.   |
| 필터/정렬     | 영화/책 필터만 제공                                     | 영화/책 필터, 최신순/별점순/제목순 정렬 제공                                                              | 목록 탐색 기능이 더 구체적이다.                   |
| 추천 기능     | 별도 추천 목록 없음                                     | 별점 4점 이상 추천 목록, 장르별 추천 필터 제공                                                            | 추천 기준이 구현과 테스트 항목으로 연결된다.      |
| 데이터 구조   | `creator`, `date`, `memo` 등 AI가 임의로 정한 항목 포함 | 설계 문서의 `title`, `type`, `genre`, `rating`, `status`, `review`, `recommended`, `recommendReason` 반영 | 설계 문서와 구현 데이터가 일관된다.               |
| UI 흐름       | 한 화면에 입력과 목록이 단순 배치됨                     | 목록, 상세, 추가/수정 모달, 추천 영역으로 역할 분리                                                       | 사용자가 기록 관리 흐름을 더 쉽게 이해할 수 있다. |
| 품질 관리     | 테스트 기준을 따로 세우기 어려움                        | 요구사항별 테스트 항목 작성 가능                                                                          | 테스트 보고서와 Lessons Learned 작성에 유리하다.  |

비교 결과, direct prompting은 빠르게 동작하는 예시를 만드는 데는 효과적이었지만, 기능 범위와 데이터 항목이 프롬프트에 따라 임의로 결정되는 한계가 있었다. 반면 프로세스 기반 결과물은 요구사항 분석과 설계 문서가 기준이 되었기 때문에 구현 결과를 검토하고 수정할 때 판단 기준이 명확했다. 특히 추천 여부 입력 방식 개선, 추천 기준 설명 보완, 테스트 보고서 작성처럼 품질 관리 단계로 자연스럽게 이어질 수 있었다.

## 4. 주요 결정 사항

- 추천 여부 체크 시 추천 이유 입력란이 표시되도록 UI를 개선한다.
- 추천 기준은 `rating >= 4`로 유지하되, 화면과 문서에서 명확히 설명한다.
- 추천 여부와 추천 목록의 의미를 구분하여 최종 보고서에 서술한다.
- 테스트 결과는 `docs/test-report.md`에 별도로 기록한다.
- direct prompting과 프로세스 기반 prompting의 비교 결과는 5차 회의록과 최종 보고서에 반영한다.
- 6차 회의에서는 최종 회고와 Lessons Learned를 중심으로 마무리한다.

## 7. 회의 후 정리

이번 회의를 통해 AI를 활용한 구현 결과를 그대로 사용하는 것보다, 회의에서 도출한 개선사항을 기준으로 수정하고 테스트하는 과정이 중요하다는 점을 확인하였다.  
특히 추천 여부 입력 방식처럼 작은 UI 요소도 사용자의 입력 흐름에 영향을 주기 때문에, 요구사항과 설계 단계에서 정한 기준을 바탕으로 구현 결과를 점검해야 한다.

또한 테스트 결과를 문서화하면서, 프로세스 기반 바이브코딩은 단순히 빠르게 코드를 생성하는 방식이 아니라 **요구사항, 설계, 구현, 테스트, 품질 관리가 연결되는 개발 방식**이라는 점을 확인하였다.
