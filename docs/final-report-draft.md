# 프로세스에 입각한 바이브코딩의 효과 분석 보고서 초안

## 1. 프로젝트 개요

본 프로젝트는 인공지능을 활용한 바이브코딩 과정에서 소프트웨어 개발 프로세스를 적용했을 때 어떤 효과가 있는지 분석하기 위해 수행하였다.  
개발 대상 소프트웨어는 영화와 책을 기록하고 추천 목록을 확인할 수 있는 웹앱 **MOBIE**로 선정하였다.

MOBIE는 사용자가 영화 또는 책 기록을 추가하고, 목록을 조회하며, 상세 내용을 확인하고 수정/삭제할 수 있는 서비스이다. 또한 별점 4점 이상인 항목을 추천 목록으로 보여주고, 장르별 추천 필터를 제공한다.

- 프로젝트명: MOBIE
- 주제: 영화/책 추천 기록 웹앱
- 개발 방식: AI를 활용한 바이브코딩
- 사용 AI: Codex, Claude, Gemini
- 형상 관리: GitHub 저장소 활용
- 산출물 위치:
  - 프로세스 기반 결과물: `output/process-based-prompting`
  - Direct prompting 결과물: `output/direct-prompting`
  - 문서 자료: `docs`

## 2. 개발 프로세스 적용 과정

### 2.1 착수 및 규칙 정의

프로젝트 초기에 팀 작업 규칙과 AI 활용 방식을 정리하였다.  
회의는 주 2~3회 진행하고, 회의록을 `docs/meetings`에 기록하기로 하였다. 또한 AI를 사용할 때는 단순히 결과물을 생성하는 데 그치지 않고, 요구사항과 설계 문서를 기준으로 결과를 검토하기로 하였다.

이 단계에서 `docs/groundrules.md`를 작성하여 다음 사항을 정의하였다.

- 회의 및 기록 방식
- 사용 AI와 역할
- GitHub 커밋 및 형상 관리 방식
- 막판 작업이 아니라 지속적인 진행을 증빙하기 위한 문서 관리 방식

### 2.2 요구사항 분석

요구사항 분석 단계에서는 MOBIE의 핵심 기능을 CRUD, 필터/정렬, 추천 기능으로 정리하였다.

기능 요구사항은 다음과 같다.

- 사용자는 영화 또는 책 기록을 추가할 수 있다.
- 사용자는 제목, 유형, 장르, 별점, 감상 상태, 한 줄 감상평, 추천 여부를 입력할 수 있다.
- 사용자는 기록 목록을 조회할 수 있다.
- 사용자는 영화/책 유형으로 기록을 필터링할 수 있다.
- 사용자는 별점순으로 기록을 정렬할 수 있다.
- 사용자는 기록 상세 내용을 확인할 수 있다.
- 사용자는 기록을 수정하거나 삭제할 수 있다.
- 사용자는 별점 4점 이상 항목을 추천 목록으로 확인할 수 있다.
- 사용자는 장르별 추천 항목을 확인할 수 있다.

비기능 요구사항은 다음과 같이 정리하였다.

- 입력 화면은 직관적이어야 한다.
- 필수 입력값이 누락되면 오류 메시지를 제공해야 한다.
- 목록은 한눈에 구분 가능해야 한다.
- 추천 기준은 명확하게 표시되어야 한다.
- 코드 구조는 유지보수가 가능하도록 분리되어야 한다.

### 2.3 설계

설계 단계에서는 화면 구조와 데이터 구조를 문서화하였다. 화면은 기록 목록, 기록 추가/수정, 상세 보기, 추천 영역으로 나누었다.  
데이터 구조는 영화와 책을 별도로 나누지 않고 하나의 공통 구조로 관리하였다.

주요 데이터 필드는 다음과 같다.

| 필드 | 설명 |
| --- | --- |
| `id` | 기록 고유값 |
| `title` | 영화 또는 책 제목 |
| `type` | 영화/책 구분 |
| `genre` | 장르 |
| `rating` | 별점 |
| `status` | 감상 상태 |
| `review` | 한 줄 감상평 |
| `recommended` | 사용자가 직접 표시한 추천 여부 |
| `recommendReason` | 추천 이유 |

이 설계는 이후 AI에게 구현을 요청할 때 기준 자료로 사용되었다.

### 2.4 구현

구현 단계에서는 두 가지 방식의 결과물을 비교하였다.

첫 번째는 짧은 프롬프트를 사용한 direct prompting 방식이다.

```text
영화/책 추천 기록 앱 만들어줘.
```

이 방식은 빠르게 실행 가능한 결과물을 만들 수 있었지만, 기능 범위가 모호하여 AI가 데이터 항목과 기능을 임의로 결정하였다. 그 결과 추가와 삭제, 간단한 필터 기능은 구현되었으나, 상세 보기, 수정, 추천 기준, 장르별 추천, 추천 이유 등 요구사항의 일부가 충분히 반영되지 않았다.

두 번째는 요구사항, 설계, 회의록을 포함한 프로세스 기반 prompting 방식이다.  
이 방식에서는 기능 요구사항, 비기능 요구사항, 데이터 구조, 화면 구조를 명시하여 AI에게 구현을 요청하였다.

그 결과 프로세스 기반 결과물에서는 다음 기능이 구현되었다.

- 기록 추가, 조회, 상세 보기, 수정, 삭제
- 영화/책 필터링
- 최신순, 별점순, 제목순 정렬
- 별점 4점 이상 추천 목록
- 장르별 추천 필터
- 추천 여부와 추천 이유 관리
- 필수 입력값 검증
- `localStorage` 기반 데이터 저장

### 2.5 테스트 및 품질 관리

테스트 단계에서는 `docs/test-report.md`를 작성하여 기능별 테스트 결과를 정리하였다.  
테스트 항목은 CRUD, 필터/정렬, 추천, 입력값 검증으로 나누었다.

4차 회의에서 발견된 주요 개선사항은 다음과 같다.

- 추천 여부를 체크했을 때만 추천 이유 입력란이 나타나야 한다.
- 추천 기준과 추천 여부의 의미를 화면에서 구분해야 한다.
- 테스트 결과를 별도 문서로 남겨야 한다.

5차 회의에서는 위 개선사항을 실제로 반영하였다.  
추천 여부를 체크하기 전에는 추천 이유 입력란을 숨기고, 체크했을 때만 표시되도록 수정하였다. 또한 추천 콘텐츠 영역에 "추천 목록은 별점 4점 이상인 기록을 자동으로 보여주며, 추천 여부는 사용자가 직접 표시한 값"이라는 설명을 추가하였다.

테스트 결과 핵심 기능은 모두 통과하였다.

## 3. Direct prompting과 프로세스 기반 prompting 비교

| 비교 항목 | Direct prompting | 프로세스 기반 prompting |
| --- | --- | --- |
| 개발 속도 | 빠르게 결과물을 생성할 수 있음 | 문서 작성 시간이 필요하지만 구현 방향이 명확함 |
| 요구사항 반영 | 기능 누락 가능성이 큼 | 요구사항 문서를 기준으로 기능을 구현함 |
| 데이터 구조 | AI가 임의로 항목을 정함 | 설계 문서의 데이터 구조를 반영함 |
| 추천 기능 | 추천 기준이 없거나 불명확함 | 별점 4점 이상, 장르별 추천 기준을 명확히 구현함 |
| 수정 가능성 | 어떤 부분을 고쳐야 할지 판단 기준이 부족함 | 회의록과 요구사항을 기준으로 수정 범위를 정할 수 있음 |
| 테스트 가능성 | 테스트 항목을 만들기 어려움 | 요구사항별 테스트 케이스를 작성하기 쉬움 |
| 보고서 작성 | 결과 중심 설명에 그칠 수 있음 | 요구사항-설계-구현-테스트 흐름을 설명할 수 있음 |

비교 결과, direct prompting은 빠른 시제품 제작에는 장점이 있었지만 과제에서 요구하는 프로세스 적용 증빙에는 한계가 있었다. 반면 프로세스 기반 prompting은 요구사항 분석부터 품질 관리까지의 흐름이 문서와 코드에 남기 때문에, 결과물의 완성도와 설명 가능성이 높아졌다.

## 4. 프로세스 적용의 교훈

### 4.1 요구사항을 먼저 정리하면 AI 결과물의 품질이 높아진다

단순히 "앱을 만들어줘"라고 요청하면 AI는 빠르게 결과물을 생성하지만, 사용자가 원하는 기능을 정확히 반영하지 못할 수 있다. 이번 프로젝트에서는 요구사항을 먼저 정리한 뒤 AI에게 전달했기 때문에 CRUD, 필터, 정렬, 추천 기능이 비교적 일관되게 구현되었다.

### 4.2 설계 문서는 AI와 사람 사이의 기준점 역할을 한다

화면 구조와 데이터 구조를 미리 정의하자, 구현 결과를 검토할 때 무엇이 맞고 무엇이 부족한지 판단하기 쉬웠다. 특히 `recommended`와 `recommendReason`처럼 추천 기능과 관련된 데이터 항목은 설계 문서가 있었기 때문에 구현 후에도 일관되게 수정할 수 있었다.

### 4.3 AI 결과물은 검토와 수정 과정을 거쳐야 한다

AI가 생성한 결과물은 처음부터 완성품이라고 보기 어렵다. 실제로 4차 회의에서 추천 이유 입력란이 항상 보이는 문제, 추천 기준 설명이 부족한 문제를 발견하였다. 이를 5차 회의에서 수정하면서 AI 활용 개발에서도 사람의 검토와 품질 관리가 필요하다는 점을 확인하였다.

### 4.4 회의록과 커밋은 개발 과정의 증빙 자료가 된다

본 과제에서는 막판에 몰아서 작업한 것이 아니라, 착수 시점부터 지속적으로 회의하고 수정한 과정을 보여야 했다. 회의록, WBS, 간트차트, 요구사항 문서, 설계 문서, 테스트 보고서를 남기면서 개발 과정 자체를 증빙할 수 있었다.

### 4.5 프로세스 기반 바이브코딩은 보고서 작성에도 유리하다

프로세스를 적용하면 단순히 "무엇을 만들었다"가 아니라 "왜 이렇게 만들었고, 어떤 기준으로 검토했으며, 무엇을 개선했는지"를 설명할 수 있다. 따라서 최종 보고서에서 요구사항 분석, 설계, 구현, 테스트, 품질 관리의 흐름을 논리적으로 서술할 수 있었다.

## 5. 한계 및 개선 방향

MOBIE는 과제 목적에 맞춰 정적 웹앱으로 구현되었기 때문에 다음과 같은 한계가 있다.

- 데이터가 브라우저 `localStorage`에 저장되어 여러 기기에서 공유되지 않는다.
- 로그인이나 사용자별 데이터 관리는 제공하지 않는다.
- 추천 기능은 별점과 장르 기준의 단순 추천에 가깝다.
- 자동화 테스트 도구를 사용한 테스트까지는 수행하지 않았다.

향후 개선한다면 서버와 데이터베이스를 연결하고, 사용자 계정별 기록 관리와 더 정교한 추천 기준을 추가할 수 있다. 또한 자동화 테스트를 도입하면 품질 관리 수준을 더 높일 수 있다.

---

## 6. 결론

이번 프로젝트를 통해 프로세스에 입각한 바이브코딩은 단순한 AI 코드 생성보다 더 안정적인 결과를 만든다는 점을 확인하였다.  
direct prompting은 빠르게 결과물을 얻는 데 효과적이지만, 요구사항 누락과 품질 관리의 어려움이 있었다. 반면 프로세스 기반 prompting은 요구사항 분석, 설계, 구현, 테스트, 개선의 흐름이 명확했으며, 회의록과 문서를 통해 개발 과정을 증빙할 수 있었다.

따라서 바이브코딩의 효과를 높이기 위해서는 AI에게 명확한 요구사항과 설계 기준을 제공하고, 생성된 결과물을 사람이 검토하며, 테스트와 회고를 통해 품질을 관리하는 과정이 필요하다. MOBIE 프로젝트는 이러한 과정을 적용한 사례이며, 프로세스 기반 개발이 AI 활용 개발에서도 여전히 중요하다는 교훈을 얻을 수 있었다.
